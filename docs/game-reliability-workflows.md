# Game workflows and reliability

Instances now have **Game workflows** and **Reliability** tabs. Features are permission checked on the server; hiding a button is not the access-control boundary. Long backup, update, maintenance and publishing operations also appear in the job center.

## Game workflows

| Feature | Supported workflow and limits |
| --- | --- |
| Sleep/wake | Modern standalone Minecraft Java servers. An optional public TCP proxy answers status pings while asleep, wakes on a login handshake, and tells players to reconnect. Ready traffic is forwarded to the loopback game listener. Status pings alone do not wake the game. Wake requests are coalesced with a 30-second retry cooldown. Idle sleep requires no proxy login connections or observed players. |
| Port bundles | Administrators reserve a main game port and up to 15 auxiliary roles using offsets and protocols. Main/query/RCON/voice/companion reservations participate in existing pool/manual collision checks. Known Minecraft, Bedrock, Valheim and ARK layouts are suggested; other games have editable roles. Main game and supported Steam query settings are applied; configure native auxiliary listeners to match. Reservations cannot detect unrelated OS listeners. |
| Managed add-on updates | Modrinth Java mods and Bukkit plugins. Resolve selected project IDs/slugs plus required dependencies, review old/new versions, and block unresolved dependencies, declared conflicts and unmanaged filename collisions. Apply to a stopped instance after staging downloads, antivirus checks and a full recovery backup. The prior add-on directory can be restored if the installed set has not changed. Untracked files are carried into the new set. Catalog metadata cannot detect every runtime conflict; test important changes in staging. |
| Staging | Administrators clone stopped managed Java/Bedrock/Steam instances onto a separate main port, use the clone's existing game/modpack update controls, test it, stop both instances, then review and promote. Source/staging file hashes invalidate stale reviews. Production identity/access/settings remain; game files, game version, loader and modpack reference are promoted. Minecraft production network properties are retained. A full pre-promotion ZIP and displaced directory provide recovery. The direct rollback refuses newer production file changes; review newer worlds and use the recorded backup when necessary. |
| World import checks | Read-only inspection of worlds uploaded to a separate instance path. Checks Java level metadata/version and region-folder presence, Bedrock level headers/LevelDB companions and edition mismatch, Terraria/tModLoader world envelope/companions, and Valheim `.db`/`.fwl` pairs. User-supplied required mod/DLC labels are compared with installed mod filenames and reported when unconfirmed. Unknown formats are explicitly unverified. This is a preflight, not a complete certification of every chunk, mod, DLC or downgrade path. |
| Configuration profiles | Private per-account profiles with up to 50 versions, pinned parent inheritance and selective files/targets. Review per-target before/after content and restart requirements. Validation and revision checks run again when applying; every target must be stopped and receives a pre-application recovery ZIP. Each version contains up to 32 files of 256 KiB; combined workflow storage is capped. Avoid putting credentials in reusable profiles. |
| Player moderation | Search observed names, join/leave history, available Java UUID/Source identity observations and private notes. Timed bans currently support running Minecraft Java servers. Expiration is dispatched when the game is running and the original operator still has permission; revoked permission creates a blocked record for review. Replacing a timed ban supersedes its old timer. Administrator-managed shared Java bans are applied explicitly to selected instances and supersede their timed bans. Check the game console for command acceptance; outside-panel changes are not synchronized automatically. |
| Minecraft profiling | Compatible spark installation required. Fixed, bounded commands start/stop/cancel a profile, request health output and sample ticks. Reports show captured viewer links, resource context, console output and investigation suggestions; expensive-plugin/mod attribution comes from the spark viewer. Explicit spark MSPT console samples feed tick alerts for two minutes. Profiling can upload to the external spark service and requires acknowledgement. |
| CS2/TF2 tournaments | Record rosters, alternate map vetoes, write stopped-game tournament presets and retain manually entered results. CS2 uses existing match/map-rotation controls; TF2 writes `tf/cfg/outpost_tournament.cfg`. Execute the preset/use existing match/demo controls after starting. Rosters are planning records; engine-enforced teams and automatic result ingestion require a compatible game plugin. |
| FastDL | Optional administrator publishing for supported Source 1 games (TF2, CSS, legacy CS:GO, GMod, HL2DM, DODS and L4D2). Publish only selected map/material/model/sound/particle assets. Files/configs/plugins/executables outside the allowlist are refused. Optional `.bz2` copies require `bzip2` on the host. Public downloads are served from `/fastdl/<instance>/...`; verification downloads/checksums up to 20 assets. Configure the displayed `sv_downloadurl`/`sv_allowdownload` settings in the game. CS2 is excluded. Limits: 1,000 paths, 128 MiB/file, 2 GiB/publication. |
| Discord | Optional signed guild slash-command endpoint. Administrators explicitly map Discord identities to existing Outpost accounts, instances and actions. Current account/access/action permissions are checked for every request; no arbitrary console command is exposed. Responses are ephemeral, replay IDs are retained and power actions have a 30-second cooldown. |

### Enabling sleep/wake

Choose a distinct public proxy port and point players/DNS at it. The game must listen on loopback or an address reachable as `127.0.0.1:<game port>`. Restrict direct backend access so players cannot bypass the proxy. Only administrators may bind listeners. The proxy supports modern Java handshakes, not Bedrock, legacy ping formats or Minecraft proxy-forwarding networks. It does not preserve client IP forwarding to the backend; consider this before enabling IP-based moderation or connection plugins. It limits initial packet size, socket count and idle handshake time.

The proxy reads protocol state to answer sleeping status requests and initiate wake. It does not retain login credentials or promise a seamless first login: clients reconnect after readiness. Wake/start still respects suspension, security holds, world-health locks and active recovery/maintenance guards.

### Staging isolation and recovery

A clone is not a network sandbox. Inspect auxiliary ports, startup arguments, public/listen addresses, external databases, shared storage and integration credentials before starting it. Java clones bind loopback and disable query/RCON; other native game settings may need adjustment. Automatic starts, automatic updates, restart loops, UPnP and panel RCON configuration are disabled on clones.

Promotion is for an unchanged production baseline. A server that accumulates newer production world data must be stopped and cloned again or merged through a game-specific process. Promotion changes files and the version/loader/modpack reference; other database-backed panel controls remain production controls. Check those controls before the first start. Previous/displaced directories are deliberately retained beside the affected directory and require administrator cleanup after successful recovery. They are not removed by snapshot retention.

If the panel restarts during a file swap, inspect the recorded full backup and retained directories before starting/retrying. A failed or interrupted operation is not automatically retried across a destructive boundary. Keep off-site backups for host/disk failure.

### Discord setup

Create a Discord application and provide its application ID, guild ID and Ed25519 public key. Configure the interaction endpoint as:

`https://<panel>/api/integrations/discord/interactions`

The raw request signature, application, guild and timestamp are verified before acting. Map the Discord user ID to an Outpost user ID, explicit instance IDs and `status`, `players`, `start`, `stop` or `restart` actions. Removing permissions/disabling the Outpost account takes effect on subsequent interactions.

To register `/outpost`, set `OUTPOST_DISCORD_BOT_TOKEN` in the host environment, restart Outpost, and use **Register guild slash command**. The token is never returned to the browser. Commands default to Discord administrator-only; grant appropriate guild command permissions separately. Existing Discord credentials or a live application are not required to run the local fixtures.

## Reliability

- **Health alerts:** configurable sustained CPU percentage, memory MiB, disk growth MiB/hour, tick time, startup duration and consecutive failed supported game queries. CPU uses the process metric (one core = 100%). Monitoring is opt-in; samples run every 15 seconds, disk growth needs a five-minute baseline, queries need fresh query results, and tick alerts need explicit recent spark output. Cooldowns and maintenance/user silencing prevent repeated notifications. Alerts include investigation suggestions and can use existing configured webhooks.
- **Maintenance:** schedule warnings and downtime across up to 32 authorized instances, validate dependency cycles, stop dependents first and restart only previously running instances in dependency order. Warnings use supported game commands; unsupported warning protocols are noted. Stop/readiness timeouts halt the run for operator review. No force kill is added by this workflow. Completed steps persist. Interrupted runs are marked for review on restart rather than blindly resumed.
- **Backup verification:** SHA-256 content verification for deduplicated snapshots and decoded ZIP CRC/size checks. Optional disposable filesystem restore tests verify extracted/copied bytes and clean up their temporary directory; they do **not** start a game, connect to external services or certify game-level recovery. ZIP verification is bounded to 1 GiB compressed, 256 MiB/entry, 20 GiB expanded and 100,000 entries. Larger files/worlds should use streaming deduplicated verification.
- **Deduplicated backups:** stopped-instance, whole-file SHA-256 storage under the configured backup location's `.deduplicated` directory. Unchanged files share blobs across retained snapshots of that instance. Storage/logical-size/savings information is shown. Retention keeps the newest snapshot in each of the configured daily, weekly and monthly UTC calendar buckets (week buckets use seven-day epochs), then removes unreferenced blobs. Defaults: 7 daily, 4 weekly, 6 monthly. This is whole-file deduplication, not changed-block backup; one modified region file requires another full file blob. ZIP backup schedules/retention remain separate. Deduplicated snapshots are created manually in this version.
- **Update preflight:** every managed `runUpdate` checks stopped/readiness state, free disk reserve, quota and platform support, plus the required Java runtime/JAR or loader arguments where applicable. Preflight failures are recorded as failed jobs; recovery steps explain how to inspect errors and restore a pre-update backup. The free-space estimate is a lower-bound reserve, not a guarantee about the size of an upstream update. Game-specific OS dependencies still need to be installed according to the game's requirements.
- **Troubleshooting:** allowlisted version/platform/runtime metadata, relevant buffered logs, small Minecraft configuration files, recent alerts, preflight and failed-job details. Authorized owners/admins also receive recent configuration change records. Credentials are redacted structurally/in text, private key blocks/webhook credentials are removed, and raw environment/launch/identity files are excluded. Review before sharing: arbitrary game/mod output can contain unexpected personal or sensitive data.

Verified recovery operations reject game starts while holding an instance stopped. Symbolic links and special files are excluded from verified backup and staged tree workflows. Full snapshot/directory recovery does not roll back Outpost's accounts, permissions, integration settings or all database-backed game controls. No backup scheme replaces off-site copies and an actual game-level recovery rehearsal.

## Validation and integration references

```powershell
npm run build --workspace=server
npm run build --workspace=web
node server/test/game-reliability-workflows.mjs
```

Set `OUTPOST_TEST_PROCESS=1` for harmless process fixtures testing maintenance order, profiler/timed-ban dispatch and Minecraft wake/forward/idle behavior. Set `OUTPOST_TEST_BROWSER_UI=1` and `OUTPOST_TEST_BROWSER` to Chromium for browser/mobile checks. Catalog downloads, game processes and Discord signatures use local/simulated fixtures; these checks do not claim certification against live game installations, a real Discord guild or a live spark service.

Protocol/integration references: [spark command usage](https://spark.lucko.me/docs/Command-Usage), [Discord interaction security and responses](https://github.com/discord/discord-api-docs/blob/main/developers/interactions/receiving-and-responding.mdx), [Source download URL](https://developer.valvesoftware.com/wiki/Sv_downloadurl).
